# Доработки технического задания

Источник проверки: `docs/TECHNICAL_TASK.MD`.

Проверка выполнена по двум наборам критериев:

1. Критерии курсового проекта из конспекта: полноценный MVP ML-сервиса, архитектура, backend, БД, очереди, auth, биллинг, Docker, ML-инференс, защита и объяснение trade-off'ов.
2. Расширенное описание проекта: JWT, Scikit-learn ML-блок, асинхронная обработка, биллинг, Streamlit dashboard, Prometheus/Grafana, тесты > 70%, бизнес-план, маркетинговые механики.

## Краткий вывод

Текущее ТЗ в целом хорошо соответствует курсовому проекту: оно описывает backend-платформу, ML-инференс, JWT, PostgreSQL, Redis/Celery, биллинг, разные цены, Docker Compose, мониторинг, тесты, демонстрационные сценарии и trade-off'ы.

Главная проблема не в отсутствии базовой идеи, а во внутренних расхождениях приоритета: часть требований, которые в критериях приемки выглядят обязательными или очень желательными, в конце ТЗ вынесена в `bonus`. Это может создать риск, что реализация будет слабее ожидаемого уровня.

## Несоответствия и риски

### 1. Prometheus/Grafana вынесены в bonus, хотя в критериях указаны как часть желательного/приемочного стека

В начале ТЗ мониторинг входит в платформенное ядро, а в Docker Compose перечислены `prometheus` и `grafana`. Но в разделе 39 `Prometheus/Grafana` указаны как bonus.

Почему это риск: в критериях отдельно указано, что мониторинг и визуализация метрик в Grafana дают сильное соответствие ожидаемому стеку. Если оставить их как bonus, можно не успеть реализовать важный критерий.

Что исправить в ТЗ:

```text
Перенести Prometheus/Grafana из bonus в минимальный MVP или в обязательные критерии приемки.
Минимум: /metrics endpoint в API, Prometheus scraping, готовый Grafana dashboard с метриками запросов, ошибок, latency, количества inference-задач и списанных кредитов.
```

### 2. Streamlit dashboard вынесен в bonus, хотя во втором наборе критериев он указан как аналитический блок

В критериях проекта отдельно указан дашборд Streamlit для статистики использования и расхода кредитов. В ТЗ есть API-аналитика, но `Streamlit UI` находится в bonus.

Почему это риск: если проверяющий ориентируется на расширенное описание проекта, отсутствие dashboard может выглядеть как невыполненный функциональный блок.

Что исправить в ТЗ:

```text
Сделать Streamlit dashboard обязательной частью MVP или явно заменить его на API-only аналитику с объяснением trade-off.
Рекомендуемый минимум dashboard:
- общий расход кредитов;
- количество запросов по дням;
- статистика по model_code;
- распределение labels;
- список последних классификаций пользователя/admin.
```

### 3. Промокоды одновременно заявлены как требование и как bonus

В биллинговом блоке промокоды указаны как функциональное требование, есть таблица `promo_codes` и endpoint активации. Но в разделе 39 `Promocodes` вынесены в bonus.

Почему это риск: противоречие в ТЗ усложняет планирование MVP и приемку.

Что исправить в ТЗ:

```text
Выбрать один статус промокодов:
1. Обязательный MVP: оставить промокоды в требованиях и добавить таблицу активаций.
2. Bonus: убрать промокоды из обязательного биллингового блока, БД и API.

Для высокого шанса на отличную оценку лучше оставить промокоды обязательными.
```

### 4. Для промокодов не хватает таблицы активаций и защиты от повторной активации

Таблица `promo_codes` хранит `used_count`, но не хранит факт активации конкретным пользователем. Без отдельной таблицы нельзя надежно запретить одному пользователю активировать один и тот же промокод несколько раз.

Что исправить в ТЗ:

```sql
CREATE TABLE promo_code_activations (
    id UUID PRIMARY KEY,
    promo_code_id UUID NOT NULL REFERENCES promo_codes(id),
    user_id UUID NOT NULL REFERENCES users(id),
    credits_granted INTEGER NOT NULL,
    activated_at TIMESTAMP NOT NULL,
    UNIQUE (promo_code_id, user_id)
);
```

И добавить приемочный критерий:

```text
Повторная активация одного и того же промокода одним пользователем возвращает ошибку и не начисляет кредиты повторно.
```

### 5. Нет явного требования к атомарности биллинга на уровне транзакций и блокировок

ТЗ говорит, что списание должно быть транзакционным и idempotent, но не фиксирует механизм защиты от race condition при параллельных задачах пользователя.

Почему это риск: преподаватель может спросить, что произойдет, если пользователь отправит несколько задач одновременно при недостаточном балансе.

Что исправить в ТЗ:

```text
Добавить требование:
- проверка баланса и списание выполняются в одной DB-транзакции;
- строка баланса блокируется через SELECT ... FOR UPDATE или эквивалентный механизм SQLAlchemy;
- баланс не может стать отрицательным;
- billing_transactions.classification_request_id уникален;
- при повторном выполнении Celery-задачи повторного списания не происходит.
```

### 6. Не определена политика резервирования средств

В flow API проверяет баланс при создании задачи, а worker списывает кредиты после успешного inference. Между этими событиями пользователь может потратить баланс на другие задачи.

Почему это риск: возникает corner case, который почти наверняка могут спросить на защите.

Нужно выбрать и описать один вариант:

```text
Вариант A: списывать только после успешного inference.
Если к моменту списания баланса не хватает, задача получает статус billing_failed, результат сохраняется как неоплаченный или не возвращается пользователю.

Вариант B: резервировать estimated_cost при постановке задачи.
После успешного inference резерв превращается в списание, после failed inference резерв возвращается.
```

Рекомендация: для более надежной архитектуры описать резервирование кредитов, потому что оно лучше закрывает параллельные запросы и недостаточный баланс.

### 7. Нет таблицы или статусов для резервирования/hold-транзакций

Если выбрать резервирование, текущей схемы `billing_transactions` недостаточно: нет статуса транзакции и типа hold/capture/refund.

Что добавить:

```sql
ALTER TABLE billing_transactions
ADD COLUMN status VARCHAR(50) NOT NULL DEFAULT 'completed',
ADD COLUMN related_transaction_id UUID,
ADD COLUMN idempotency_key VARCHAR(255) UNIQUE;
```

Рекомендуемые `transaction_type`:

```text
initial_grant
top_up
promo_grant
inference_hold
inference_capture
inference_refund
admin_adjustment
cache_hit_charge
```

### 8. Нет полноценной системы уровней биллинга/лояльности, хотя она указана как продвинутый вариант

ТЗ содержит rate limiting по планам Free/Pro/Enterprise и разные цены моделей, но не описывает уровни Bronze/Silver/Gold, скидки и ежемесячный пересчет.

Почему это важно: критерии прямо предлагают маркетинговые механики как вариативную часть. Промокоды уже есть как базовый вариант, но если нужен более сильный проект, стоит добавить уровни.

Что добавить как optional advanced requirement:

```text
Loyalty tiers:
- Bronze: базовый уровень, скидка 0%;
- Silver: >= 50 успешных предсказаний за месяц, скидка 5%;
- Gold: >= 200 успешных предсказаний за месяц, скидка 10%.

Раз в месяц Celery Beat задача пересчитывает уровень пользователя по статистике completed inference за прошлый месяц.
Стоимость inference рассчитывается как base_model_price * (1 - discount_percent).
```

Минимальные таблицы:

```sql
CREATE TABLE loyalty_tiers (
    id UUID PRIMARY KEY,
    code VARCHAR(50) UNIQUE NOT NULL,
    min_monthly_predictions INTEGER NOT NULL,
    discount_percent INTEGER NOT NULL,
    is_active BOOLEAN NOT NULL DEFAULT TRUE
);

ALTER TABLE users ADD COLUMN loyalty_tier_id UUID REFERENCES loyalty_tiers(id);
```

### 9. Нет реферальной программы и cashback, если выбирать экспертный вариант

Если нужен экспертный уровень, добавить:


Расширенное описание проекта говорит об интеграции с платежным шлюзом для пополнения баланса. Текущее ТЗ использует mock endpoint, что нормально для курса, но это нужно явно объяснить как trade-off.

### 14. Не определен Celery Beat/cron для периодических задач

Если остаются только промокоды, cron не обязателен. Но если добавлять уровни лояльности, cashback или очистку старых задач, нужен Celery Beat.

Что добавить:

```text
Celery Beat задачи:
- monthly_recalculate_loyalty_tiers, если включены уровни;
- expire_old_promo_codes или проверка valid_until при активации;
- optional: cleanup_old_failed_tasks.
```

В разделе 15.5 batch endpoint описан как часть API, но в разделе 39 batch classification указан как bonus.

Что исправить:

```text
Либо перенести batch classification в MVP, либо пометить endpoint как optional и убрать из обязательного API.
Если оставить batch в MVP, нужно описать атомарность биллинга:
```

### 16. Cache pricing не определен однозначно

ТЗ говорит, что кешированный результат стоит `0 или 1 credit`. Для биллинга это слишком неопределенно.

Что исправить:

```text
Выбрать одно правило.
Рекомендуемое MVP-правило: cache hit стоит 1 credit, потому что пользователь все равно получает сервисный результат, но дешевле обычного inference.
Альтернатива: cache hit бесплатный, но только если запрос был ранее сделан тем же пользователем.
```

## Предлагаемый новый раздел для вставки в ТЗ

```markdown
# Критерии приемки MVP

MVP считается готовым, если:

1. Проект запускается одной командой `docker-compose up`.
2. Поднимаются `api`, `worker`, `postgres`, `redis`, `prometheus`, `grafana`.
3. Swagger доступен по `/docs`, все endpoint'ы имеют Pydantic-схемы.
4. Пользователь может зарегистрироваться, авторизоваться через JWT и получить стартовый баланс.

6. Celery worker выполняет ML inference через `BaseClassifier` и `ModelRegistry`.
7. Сервис поддерживает модель `prompt_guard`.
8. Успешный inference атомарно списывает кредиты.
9. Failed inference не списывает кредиты.
10. Повторное выполнение одной Celery-задачи не приводит к повторному списанию.
11. Недостаточный баланс обрабатывается явно и не допускает отрицательный баланс.
12. Промокод нельзя активировать повторно одним пользователем.
13. Есть история классификаций и история billing transactions.
14. Grafana показывает метрики API, worker, ошибок, latency и списанных credits.
15. Тесты запускаются через `pytest`, покрытие не ниже 70%.
16. В `docs/` есть `architecture.md`, `billing.md`, `tradeoffs.md`, `business_plan.md`, `demo_scenarios.md`.
```

## Итоговая оценка ТЗ

ТЗ уже сильное и по архитектуре даже шире минимальных требований. Основные доработки нужны не для смены идеи, а для устранения неоднозначностей:

- что является MVP, а что bonus;
- как именно защищен биллинг от повторных списаний и гонок;
- какая маркетинговая механика выбрана;
- где формально закреплены Swagger, dashboard, monitoring, coverage и business plan.

После внесения этих правок ТЗ будет лучше соответствовать и конспекту, и расширенному чек-листу приемки.
